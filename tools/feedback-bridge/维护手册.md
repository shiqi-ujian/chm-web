# chm-web 问题处理维护手册（Agent SOP）

> 本手册是 agent 每次被定时唤醒后对 chm-web 项目（`E:\yingren\shiqi-ujian-chm-web`）的处理规程。唤醒源：主会话 dsh-schedule 每 60 分钟统一巡检（4AD / 5z / chm-web 三项目一轮完成）。
> 相关路径均相对仓库根 `E:\yingren\shiqi-ujian-chm-web`。

## 0. 职责

群友通过腾讯文档收集表（链接发 QQ 群）提交问题 → 系统定时读取到 `问题收集/inbox/` → 本 agent 自动 debug、修复、发布（push main → 阿里云自动拉取部署），并把结果写入 `CHANGELOG.md` 公示。

**安全铁律（违反即事故）**：
- `问题收集/`、`tools/feedback-bridge/config.json`、共享登录 profile、`feedback-state.json` 都已在 .gitignore 中，**严禁** `git add` 或提交其中任何内容（公开仓库）。
- 推送前必须 `git status --short` 检查变更清单，确认无敏感文件（`*.pem`、`部署与环境备份_勿上传git.txt` 等）。
- 生产数据（上传的 CHM、账号）在服务器持久卷，本地 `data/` 不入库；修复时**不要**动本地 `data/` 下的真实样本数据。

## 1. 每轮处理流程

1. **读告警**：检查 `问题收集/alerts.md`（读取桥写入的告警）。有内容 → 先处理（如提示用户重新登录），处理完清空该文件。
2. **读取收集表**：运行 `node tools/feedback-bridge/collect-docs.mjs`（或确认读取桥/手动导入已把新问题放进 `问题收集/inbox/`）。
3. **列出 inbox**：`问题收集/inbox/*.json` 全部为待处理。无新问题 → 一句话结束本轮，不输出长文。
4. **逐条处理**（见第 2、3 节）：
   - 能定位并安全修复 → 修复 + 校验 → 计入本批发布。
   - 无法复现 / 描述不清 → `status: "need-info"`，在 `resolution` 写明缺什么信息，记入 CHANGELOG 的待确认段公示。
   - 需要用户决策 → `status: "blocked"`，在会话里说明并留待用户处理。
5. **发布**（本批有修复时）：见第 4 节。
6. **更新日志**：见第 5 节。
7. **收尾**：处理完的 inbox 文件移入 `问题收集/done/`（保留原 JSON，`status` 更新为 done，`resolution`/`released`/`doneAt` 填好）。

## 2. 修复来源定位表

| 问题类型 | 修复位置（源） | 说明 |
|---|---|---|
| 后端逻辑 bug（上传/转换/权限/导出/搜索 API） | `src/lib/*.js`、`src/`（auth.js、convert、export、search 等） | 改后跑对应 `test-*.js` 回归 |
| CLI / 批量脚本 | `bin/cli.js`、`scripts/`、`tools/rebuild-*.js` | `node bin/cli.js --help` 查看子命令 |
| 阅读壳/欢迎页/上传页前端 | `src/` 内模板或 `tools/rebuild-shells.js`、`rebuild-landing.js` 生成物 | 改模板源后重跑生成器（参照「生成页整页 JS 失效两连坑」：改模板产物必须改模板源） |
| 构建/部署 | `Dockerfile`、`.deploy-tools/*` | 部署脚本改动风险高，改后演练再发布 |
| 站点索引 | `docs/_index.json`（运行时生成） | 不手改 |

定位辅助：先在线上站点复现/核对问题，再反查 `src/` 源码。测试文件 `test-*.js` 是了解行为的入口（README 里程碑章节按模块列了验收）。

## 3. 校验

- JS 语法：`node --check <文件>`
- 模块回归：`node test-<模块>.js`（如 `node test-auth.js`、`node test-export-docs.js`）
- 全套：`npm test`（约 17 个测试文件串联；发布前至少跑改动相关模块 + 冒烟）
- 页面交互验证：参照 5z 模式写临时无头 Edge CDP 验证脚本（`_test-*.mjs`，gitignore 已忽略）

## 4. 发布

```bash
git add -A
git commit -m "fix: 修复 <问题id> <标题>（若为多问题批量：fix: 修复反馈问题 <ids>）"
git push
```

- 发布 = push main → GitHub → 阿里云自动拉取构建部署（Docker 容器 `chm-web`，`--restart unless-stopped`，数据在持久卷）。
- 发布前先 `git status --short` 检查变更清单（确认无 `问题收集/`、`*.pem`、部署令牌等敏感文件）。
- 推送失败：remote 是 **SSH**（`git@github.com:shiqi-ujian/chm-web.git`）。先重试一次；再失败检查 ssh-agent / GCM 凭据；仍失败则保留本地提交，在会话中提示用户，下次巡检先 `git status` 补推。
- 若线上异常需手动干预：`.deploy-tools/ssh-run.js` 可远程执行（谨慎使用），`deploy.sh` 的 start/restart/logs 由服务器运维执行。

## 5. 更新日志维护

- 在 `CHANGELOG.md` 顶部追加本批小节（倒序，最新在上）：
  - `## YYYY-MM-DD` + 修复条目（含问题 ID、原因、影响范围）；无法处理的记入「待确认」段。
- 随本批发布一并提交。

## 6. 特殊情形

- **读取桥告警（alerts.md 有内容）**：通常是未登录或页面结构变化 → 提示用户运行 `tools/feedback-bridge/login-docs.bat` 重新登录（共享 profile，一次登录覆盖 4AD + chm-web），或 `collect-docs.mjs --probe` 后根据输出校准提取逻辑；期间可继续处理已入库问题。
- **表单截图附件**：读取桥尽力下载到 `问题收集/attachments/<id>/`，缺失时按描述判断即可。
- **重复问题**：读取桥按内容哈希去重；处理时若发现与 done 中问题重复，合并并注明。
- **涉及生产数据/无法本地复现**：标 need-info 或 blocked，不盲目改代码。

## 7. 运行前提（提醒用户）

- Harness 服务运行中，且主会话保持打开（schedule 到期才能准时唤醒；关闭期间到期项会在重开后补处理）。
- 读取桥共享登录态有效（定期用 `login-docs.bat` 刷新）。
- Node.js、git 凭据可用（SSH key 或 PAT）。
